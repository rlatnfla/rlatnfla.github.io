Java 애플리케이션을 실행하는 순간, JVM은 운영체제로부터 실행에 필요한 메모리를 할당받아 실행 엔진(Execution Engine)과 함께 프로그램을 구동시킨다.

이렇게 OS로부터 할당받은 JVM 고유의 메모리 영역을 **JVM 런타임 데이터 영역(Runtime Data Area)** 이라고 부른다.

이 영역이 어떻게 구성되어있는지, 그리고 우리가 작성한 코드가 이 메모리 위에서 어떤 생명주기를 갖는지 그 구조에 대해 자세히 알아보겠다.

---

## 1. JVM Runtime Data Area 구조

구조 이미지

Runtime Data Area, 줄여서 RDA는 스레드별로 메모리 공간을 공유하는 Shared Area와 그렇지 않은 Thread-Local Area로 나눌 수 있다.

---

## 2. Shared Area

Shared Area는 모든 스레드에서 접근 가능한 공유 자원의 영역이다. 

Java 애플리케이션이 실행되거나 JVM이 시작될 때 단 하나만 생성되며, 모든 스레드가 이 공간을 공유하기 때문에 명확한 특징이 있다.

- **높은 자원 효율성:** 클래스 설계도나 객체들을 스레드마다 따로 만들지 않고 한 곳에 집중시켜 놓기 때문에 메모리 공간을 효율적으로 사용할 수 있다.
- **데이터 공유:** 서로 다른 스레드가 동일한 데이터와 객체를 참조 할 수 있으므로 실시간으로 값을 주고 받을 수 있다.
- **동시성 이슈:** 데이터 공유가 가능하다는 사실은 **필수적으로 Race Condition 과 같은 동시성 이슈를 수반한다.** 
- **메모리 관리:** 많은 스레드에서 해당 영역에 데이터를 생성하고 사용하지만, 더이상 참조되지 않는 데이터가 자동으로 해제되지 않기 때문에 메모리 관리가 필수적이며, 이를 위해 **GC(Garbage Collector)** 가 등장하였다.

이러한 Shared Area는 관리하는 데이터의 목적에 따라 크게 세 가지 구역으로 나뉜다.

### 1) Method Area (Metaspace)

메서드 영역이란 쉽게말해 클래스/인터페이스의 설계도 정보가 할당되는 영역이다.

- **클래스/인터페이스 메타데이터:** 이름, 부모클래스, 접근 제어자등
- **필드 & 메서드 정보:** 변수, 데이터 타입, 메서드 시그니처, 실제 실행될 바이트코드 명령어
- **static 변수:** 특정 인스턴스(`new`)의 소유가 아니라 클래스 자체에 종속되어 프로그램 시작부터 종료까지 살아남아야 하는 자원들이므로 메서드 영역에 할당된다.
- **Runtime Constant Pool (런타임 상수 풀):** 클래스 파일의 Constant Pool을 런타임에 메모리로 올려놓은 자료구조로, 문자열 리터럴뿐 아니라 클래스, 필드, 메서드 참조 정보 등을 저장한다.

>Java 8 HotSpot JVM에서는 클래스 메타데이터와 Runtime Constant Pool은 Metaspace에 저장되지만, static 필드의 실제 값과 String Pool의 문자열 객체는 Heap에 저장되며 GC의 관리 대상이 된다

사실 'Method Area' 라는 용어는 JVM 명세서에 적힌 **논리적인 개념** 에 가깝다. Java 버전에 따라 이 개념이 실제로 메모리에 구현된 형태는 완전히 다르다.

**Java 7 이하 버전**에서는 물리적으로 JVM의 힙(Heap) 영역 내부에 `Perm Gen (Permanent Generation)`이라는 제한된 크기의 메모리 공간을 할당받아 사용하였다.

> Java 7 HotSpot JVM
```text
<----- Java Heap ----->             <--- Native Memory --->
+------+----+----+-----+-----------+--------+--------------+
| Eden | S0 | S1 | Old | Permanent | C Heap | Thread Stack |
+------+----+----+-----+-----------+--------+--------------+
                        <--------->
                       Permanent Heap
S0: Survivor 0
S1: Survivor 1
```

`Perm Gen` 영역은 최대 값이 제한되어있는 Heap 영역에 위치하기 때문에 최대 크기를 넘어서는 순간 컴퓨터의 가용 RAM 용량이 충분하더라도 `OutOfMemoryError: PermGen space`와 함께 애플리케이션이 종료되는 문제가 발생했다.

이러한 문제 때문에 **Java 8 이상 버전**부터 `Perm Gen`이 없어지고 `Metaspace`가 도입되었다. 가장 큰 차이점은 `Metaspace`는 더이상 Heap 영역에 위치하지 않고 크기가 가변적인 **Native Memory Area**에 위치해있다는 점이다.

> Java 8 HotSpot JVM
```text
<----- Java Heap -----> <--------- Native Memory --------->
+------+----+----+-----+-----------+--------+--------------+
| Eden | S0 | S1 | Old | Metaspace | C Heap | Thread Stack |
+------+----+----+-----+-----------+--------+--------------+
```

필요에 따라 확장이 가능한 `Metaspace`의 도입 덕분에 `Perm Gen`에 비해 OOM 발생 가능성이 크게 감소하였다.

다만 이 역시도 무한정 확장되는 것이 아니기 때문에 클래스 메타데이터가 과도하게 증가하면 `OutOfMemoryError: Metaspace`가 발생할 수 있다.

### 2) Heap

Heap 영역이란 참조 타입 인스턴스의 실제 데이터가 할당되는 공간이다. 

`new` 키워드로 인스턴스를 생성하면 오브젝트 헤더 데이터와 인스턴스 데이터 등이 Heap 영역에 동적으로 저장된다.

**여기서 가장 중요한 점은, JVM 내의 그 어떠한 영역도 이 힙 영역의 무거운 데이터를 본인의 영역으로 직접 복사해 가지 않는다는 점이다.**

스레드가 동작하는 공간인 스택(Stack) 영역이나, 다른 인스턴스 내부의 참조 필드값들은 힙 영역에 저장된 실제 데이터를 본인 영역에 재할당 하지 않는다.

대신, 스택 영역의 **지역 변수 테이블(Local Variable Table) 엔트리**나 인스턴스 내부의 **필드 데이터 공간**에 힙 인스턴스의 **물리적인 메모리 주소**를 저장해 둔다. 그리고 필요시 이 주소를 통해 힙 영역에 접근하여 데이터를 참조하는 방식으로 동작한다.

### GC(Garbage Collector) 의 필요성

스택(Stack) 영역은 스레드가 메서드를 실행할때 생성되고 지역 변수를 위한 공간을 할당하며 메서드를 실행 한 뒤에 메서드가 종료될때 해제된다.

그러나 JVM은 메서드 내부에서 생성된 인스턴스와 같은 힙 영역의 공간까지는 해제하지 않는다.

이때 힙에서 메모리 공간을 차지하면서도 그 누구에게도 참조되지 않는 **유령 인스턴스(Unreachable Object)** 들이 생겨나는데, 이러한 유령 인스턴스들을 해제하여 메모리 공간을 확보하는 역할을 하는 것이 바로 `GC(Garbage Collector)`이다. 

코드로 예시를 들어보겠다.
```java
public void makeUser(int age) {
    User user = new User();
    user.setAge(age);
}
```

파라미터인 `age`는 원시 타입(int) 이므로 스택의 지역 변수로서 메모리를 할당받고, 메서드 종료시 스택과 함께 해제된다.

반면 `User`는 참조 타입이기 때문에 `new User()`를 통해 생성된 `user`라는 인스턴스는 힙 영역에 메모리를 할당받고, 지역 변수 테이블 엔트리에 물리적 주솟값을 저장한다.

메서드가 종료된 뒤 스택 프레임이 해제되어도 `user` 인스턴스의 데이터는 힙 영역에 계속해서 살아있게 된다.

특히 해당 메서드는 생성된 인스턴스를 리턴하지 않기 때문에, 만약 이 메서드가 애플리케이션의 여러곳에서 호출되거나 반복문 내부에서 무수히 호출되는 경우 힙 영역 메모리 부족이 발생할 수 있다.

`GC`는 여러 알고리즘과 힙 영역의 세분화된 구조를 활용하여, 참조가 끊어진 유령 인스턴스들을 찾아내 해제함으로써 힙 영역의 메모리 공간을 확보한다.

자세한 `GC`의 동작 매커니즘과 힙의 세부 구조(Eden, Survivor, Old)는 다른 포스팅에서 더 깊게 다루어 보겠다.

## 3. Thread Local Area

Thread Local Area는 Shared Area와 정반대 되는 개념으로, **스레드 별로 독립적으로 구성되는 메모리 공간**이다.

스레드 로컬 영역의 생명 주기는 스레드와 동일하다.

> 이곳에 thread local area 구조 이미지 첨부하시오

스레드 로컬 영역의 세가지 구성 요소에 대해서 하나 씩 알아보겠다.

### 1) JVM Stack (Method Stack)

> 이곳에 메서드 스택 구조 이미지 첨부하시오

메서드 스택이라고도 불리는 이 공간은 스레드가 메서드를 실행하는 공간이다. 이름에서도 알 수 있듯이 자료구조 **스택(Stack)** 으로 이루어져 있다.

메서드 스택은 메서드를 실행하기 위해 목적에 따라 세가지 영역에 데이터를 저장한다.

#### Local Variables (지역 변수 테이블, LVT)
메서드의 매개변수(Parameter)와 내부에서 선언된 지역 변수가 저장되는 공간이다.

LVT는 `0`번 인덱스부터 시작하는 슬롯구조로 관리되는데, 호출된 메서드의 성격(`static` 여부)에 따라 인덱스 배치에 차이가 있다. 

- **스태틱(static) 메서드:** `0`번 인덱스부터 매개변수가 순서대로 저장된다.
- **인스턴스 메서드:** `0`번 인덱스에 `this`라는 이름으로 현재 인스턴스의 힙 영역 주소값을 저장한다. 이후 `1`번 인덱스부터 매개변수들이 차례대로 저장된다.

매개변수들의 배치가 끝난 공간 뒤로는, 메서드가 실행되면서 코드 흐름에 따라 지역 변수들이 선언되는 시점에 순차적으로 공간(슬롯)이 할당된다.

할당된 공간(슬롯)에 값이 채워지는 것은 해당 지역변수의 초기화/대입 시점이다.

#### Operand Stack (피연산자 스택, OS)

LVT에 할당된 변수들을 가지고 연산(산술, 논리, 객체 생성 등)을 처리하는 가상의 작업 공간이다.

소스코드가 `javac`에 의해 컴파일되면, 내부 연산 로직들은 `iload`, `iadd`와 같은 JVM 표준 바이트코드 명령어로 변환된다.

```text
iload_1
iload_2
iadd
istore_3
```

위 바이트코드는 LVT의 1번과 2번 엔트리에 있는 값을 차례대로 피연산자 스택에 넣고(push), 연산자(iadd)를 만나면 스택 최상단(Top)에서부터 데이터 2개를 꺼내(pop) 더한 뒤, 그 결과값을 다시 스택에 넣는(push) 일련의 과정을 보여준다.

여기서 주목할 점은 **이 과정 어디에서도 "값을 어떤 하드웨어 레지스터에 임시 저장하고 연산할 것인지", "결과는 어떤 레지스터에 저장할 것인지"에 대한 구체적인 명시를 찾아볼 수 없다는 것**이다.

자바는 바이트코드 수준에서 레지스터 구조를 의도적으로 노출하지 않도록 설계되었다. 이를 통해 자바는 어떤 환경에서든 동일하게 실행될 수 있는 플랫폼 독립성(WORA)을 얻었고, 컴파일러가 복잡한 레지스터 분배 알고리즘을 계산할 필요가 없어지면서 **컴파일 과정 또한 매우 가볍게** 유지할 수 있게 되었다. 

또한, 바이트코드의 크기도 줄일 수 있어 당시 Applet과 네트워크 다운로드 환경에 적합했다.

나아가 이러한 스택 머신의 구조는 타입 검증(Bytecode Verification)과 인터프리터 구현난이도를 상대적으로 낮추어 JVM 구현에도 유리하다는 장점이 있다.

#### Frame Data

Frame Data는 스택 프레임 내에서 지역 변수(LVT)와 피연산자 스택(OS)을 제외한, 메서드의 안전한 실행과 제어를 지원하기 위한 메타데이터 정보를 총칭하며 크게 4가지 영역으로 구분된다.

1. **런타임 상수 풀 참조**
    - 스택 프레임이 생성되는 시점에 **해당 메서드가 속한 클래스의 런타임 상수 풀 메모리 시작 주소**를 포인터 형태로 주입받아 저장한다.
    - 인터프리터는 바이트코드를 실행하다가 외부 참조 번호표(#)를 마주치면, 이 참조 주소를 사용하여 Metaspace 내의 런타임 상수 풀로 직행하여 필요한 데이터를 읽어낸다.
2. **다이나믹 링킹 (Dynamic Linking)**
   - 바이트코드에 포함된 **클래스, 필드, 메서드에 대한 심볼릭 참조(Symbolic Reference)를 런타임에 실제 참조(Direct Reference)로 해석(Resolution)하여 연결하는 과정**이다.
   - 이 과정에서 현재 스택 프레임은 자신이 속한 클래스의 런타임 상수 풀 참조를 이용하며, JVM은 Runtime Constant Pool에 저장된 심볼릭 참조를 이용하여 실제 클래스 메타데이터와 필드, 메서드 정보를 찾아 연결한다.
   - 따라서 다이나믹 링킹 자체는 Frame Data에 저장되는 정보라기 보다는 런타임 상수 풀 참조를 이용하여 수행되는 런타임 작업(process)이라고 볼 수 있다.
3. **복귀(Return)관련 제어 정보 & Normal Method Completion** 
   - 메서드가 모든 로직을 정상적으로 수행하고 종료될때, **자신을 호출한 부모 메서드로 안전하게 복귀하기 위해 필요한 제어 정보와 처리과정**이다.
   - 호출자 메서드의 스택 프레임으로 복귀하기 위한 제어 정보와, 호출자 메서드의 실행을 재개할 위치(Return Address)를 유지한다.
   - **런타임 수행 과정** 
     1. 현재 메서드에 Return Value가 존재한다면, 현재 스택프레임이 제거되기 전에 그 값을 **부모 메서드 스택프레임의 Operand Stack에 `push`** 한다.
     2. 현재 메서드의 스택 프레임을 JVM Stack에서 완전히 제거(`pop`)한다.
     3. 프레임 데이터에 저장해 두었던 복귀 주소를 바탕으로 호출자 메서드의 실행 위치를 복원하고, 호출자가 다음 동작을 수행하도록 제어권을 반환한다.
4. **예외 처리 제어 정보 & Abrupt Method Completion**
    - 메서드 실행 중 예외 객체가 발생(Throw)되었으나 현재 메서드 내부에서 이를 수습(catch)하지 못해 **메서드가 정상적인 결과를 반환하지 못하고 비정상적으로 종료되는 과정과 이를 제어하기 위한 정보**이다.
    - 현재 메서드의 예외 처리 흐름을 제어하기 위해, JVM은 메서드 메타데이터(Metaspace)에 저장된 **Exception Table** 에 접근할 수 있는 정보를 유지한다.
    - **런타임 수행 과정**
      1. 메서드 실행 중 예외가 발생하면, JVM은 현재 메서드의 **예외 테이블 (Exception Table)** 을 검색한다. 해당 테이블에는 예외가 발생한 바이트코드의 위치(PC)를 처리하는 예외 처리기(Exception Handler) 정보가 명시되어 있다.
      2. **[내부 수습 성공 시]:** 발생한 예외를 처리할 수 있는 일치하는 예외 처리기를 예외 테이블에서 찾았다면, JVM은 현재 스택 프레임을 유지한 채 해당 예외 처리기의 바이트코드 위치로 PC 레지스터를 변경(Jump)하여 실행을 계속한다.
      3. **[내부 수습 실패 시]:** 현재 메서드가 발생한 예외를 처리할 수 있는 예외 처리기를 찾지 못하면, 해당 메서드는 예외를 호출자에게 전파(Throw)하며 비정상 종료(Abrupt Method Completion)된다. 이 경우 현재 메서드는 정상적인 return을 수행하지 못한 채 **자신의 스택 프레임을 JVM Stack에서 즉시 제거(`pop`)** 한다.
      4. 이후 발생한 예외 객체를 자기를 호출했던 호출자 메서드로 그대로 던져버리며(Throw), 제어권을 넘겨받은 호출자 메서드의 스택프레임에서 다시 첫 번째 과정(예외 테이블 검색)부터 이 예외를 처리 할 수 있는지 재탐색을 시작한다. 이를 **Stack Unwinding**이라고 하며, 최종적으로 처리기가 발견되지 않으면 JVM은 해당 스레드를 종료시키고 Uncaught Exception을 보고한다.
